# Цель

Этот документ определяет обязательные правила разработки проекта и обязателен для любого разработчика или AI-агента, который вносит изменения в репозиторий.

# Главные источники истины

1. MOTIVATION.md
2. REQUIREMENTS.md
3. DOMAIN_MODEL.md
4. SYSTEM_ARCHITECTURE.md
5. Исходный код проекта

Если возникает противоречие между документами и кодом, приоритет всегда отдается более раннему документу в списке.

# Правила разработки

- Не добавлять функции, которых нет в REQUIREMENTS.md.
- Не изменять архитектуру без необходимости и без явной привязки к требованиям.
- Не менять бизнес-логику без анализа: сначала проверить соответствие MOTIVATION.md и REQUIREMENTS.md.
- Не удалять существующий функционал без веской причины и полного понимания влияния.
- Минимизировать изменения: править только тот код, который необходим для реализации требования.
- Соблюдать существующий стиль проекта и существующие соглашения.
- Использовать существующие сервисы и слои при расширении логики, а не дублировать функциональность.
- Избегать дублирования логики между слоями backend и frontend.
- Не внедрять новые архитектурные слои или шаблоны, не описанные в SYSTEM_ARCHITECTURE.md, без явного пересмотра архитектуры.
- Любое изменение должно документироваться в соответствующих документах, если меняется поведение, модель данных или архитектура.

# Процесс разработки

Шаг 1

Изучить документацию:
- MOTIVATION.md
- REQUIREMENTS.md
- DOMAIN_MODEL.md
- SYSTEM_ARCHITECTURE.md

↓

Шаг 2

Определить требование, которое реализуется, и его источник.

↓

Шаг 3

Найти соответствующий код:
- backend: routes, controllers, services, middleware, database
- frontend: pages, компоненты, API client, типы

↓

Шаг 4

Составить план изменений:
- какие модули затрагиваются;
- какие данные изменяются;
- как это влияет на взаимодействие между слоями.

↓

Шаг 5

Проверить влияние на архитектуру:
- не нарушит ли изменение REST-схему;
- не нарушит ли роль `ADMIN` / `OWNER`;
- не создаст ли лишних зависимостей между frontend и backend.

↓

Шаг 6

Только после подтверждения изменять код.

↓

Шаг 7

После завершения работы проверить и обновить документацию, если изменилось:
- мотивация;
- требования;
- бизнес-модель;
- архитектура.

# Правила изменения Backend

### Controller

- Контроллеры должны оставаться тонкими: проверка запроса, авторизация, выбор контекста и вызов сервисов.
- В контроллере не должна содержаться сложная бизнес-логика или доступ к данным.
- Новые сценарии должны реализовываться через сервисы.
- Запрещено перемещать логику из сервисов в контроллер без необходимости.

### Service

- Сервисы содержат CRUD и бизнес-логику.
- В сервисе реализуются правила предметной области: проверка подписки, доступность магазина, работа с вариантами товара, аналитика, AI draft.
- Если логика затрагивает несколько сущностей, она должна быть в сервисе, а не в контроллере.
- Запрещено дублировать код из других сервисов.

### Middleware

- Middleware отвечает за авторизацию и проверку ролей.
- Middleware не должна содержать бизнес-логику предметной области.
- Проверка JWT и роли должна оставаться в `authMiddleware.ts` и `adminOnly` / `ownerOnly`.
- Запрещено добавлять логику обработки данных продукта или магазина в middleware.

### Database

- Изменения в схеме должны отражать реальные данные, описанные в DOMAIN_MODEL.md и SYSTEM_ARCHITECTURE.md.
- Нельзя создавать отдельные сущности, не описанные в текущей модели, без пересмотра архитектуры.
- Данные подписки хранятся в магазине, AI draft не является отдельной таблицей.
- Запрещено дублировать структуру сущностей в базе и в коде.

# Правила изменения Frontend

### Pages

- Страницы должны реализовывать конкретный пользовательский сценарий.
- Логика бизнес-правил на уровне страниц должна быть минимальной.
- Для управления магазином, товарами, админкой и витриной использовать существующие страницы.
- Запрещено создавать новые страницы, если требование может быть реализовано на существующей.

### Components

- Создавать новый компонент только если он повторно используется или улучшает читаемость текущих страниц.
- Компонент должен быть простым и отвечать одной задаче.
- Компоненты не должны содержать сложной бизнес-логики.
- Запрещено разбивать простую страницу на множество специальных компонентов без необходимости.

### API Client

- Все HTTP-запросы должны идти через `api/client.ts`.
- JWT должен всегда браться из `localStorage` и добавляться в заголовок `Authorization`.
- Новые запросы должны соответствовать существующим маршрутам backend.
- Запрещено дублировать конфигурацию Axios в других модулях.

### Types

- Типы должны отражать существующую модель предметной области.
- Не создавать новые типы, противоречащие DOMAIN_MODEL.md, без согласования.
- Типы должны соответствовать структуре ответов API и полям базы.

# Работа с AI

- AI помогает разработчику, но не принимает архитектурные решения.
- AI не должен самостоятельно менять архитектуру или добавлять новые функции.
- AI обязан сначала анализировать документы и существующий код.
- Любое предложение от AI должно проверяться человеком перед внедрением.
- Новая AI-логика должна соответствовать MOTIVATION.md и REQUIREMENTS.md.
- Если в коде есть несовпадение с документами, AI должно описать расхождение, но не исправлять его самостоятельно.

# Работа с документацией

После каждого изменения необходимо определить, изменилось ли:
- мотивация;
- требования;
- бизнес-модель;
- архитектура.

Если хоть один из этих элементов изменился, необходимо обновить соответствующий документ:
- MOTIVATION.md — только если изменяется цель и бизнес-мотивация.
- REQUIREMENTS.md — если меняется поведение системы и требования к системе.
- DOMAIN_MODEL.md — если меняется предметная модель.
- SYSTEM_ARCHITECTURE.md — если меняется архитектурное строение системы.

# Контрольный список

Перед завершением любой задачи необходимо проверить:

□ Требование реализовано.

□ Архитектура не нарушена.

□ Дублирования нет.

□ Лишний код отсутствует.

□ Документация актуальна.

□ Все изменения минимальны.
